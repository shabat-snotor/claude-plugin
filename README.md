# Snotor skill library

The team's shared ways of working, written down so Claude does them the same way for everyone: writing a ticket, reviewing a document, handing over a feature, checking a query.

Anyone can add or improve one. You do not need to know git, markdown, or what a skill is. You talk to Claude, try the result on something real, and it goes out to the team.

## Change or add a skill

**Type `/skill` and describe what you want.** That is the whole workflow, and it is the same for a designer, a product owner, and a developer.

```
/skill
/skill the ticket skill keeps burying the summary
/skill I want one that turns Figma comments into a QA checklist
```

Claude then:

1. **Checks the catalog** for something that already does the job, and says so if there is one. Improving an existing skill almost always beats adding a near-duplicate.
2. **Asks a few questions**, the important one being "show me one example of a good result". A single real example is worth more than a page of description.
3. **Writes the skill.**
4. **Tries it on real work** and shows you the output. You say whether that is what you wanted. This repeats until it is.
5. **Publishes it**, and tells you in one line what changed.

There is no review step and no approval. Step 4 is the quality gate: nothing ships that the author has not watched work. If something does go out wrong, `/skill` also undoes it, and every earlier version stays in the history.

### Changing a skill that already exists

This is the more common half, and the half with the risk in it: creating a skill can only add something, while changing a shared one can take away behaviour other people were relying on. `/skill` handles the difference for you, but it is worth knowing what it is doing.

- It reads the **whole** current file, never a reconstruction from memory, and looks at what changed recently so your fix does not quietly undo someone else's deliberate one.
- It prefers making a vague rule specific over adding a new rule. A skill that grows a section every time someone is disappointed becomes a skill nobody reads.
- It test-drives **twice**: once on the case that prompted the change, and once on a case the skill already handled well. The second run is the regression check, and it is the only thing between a well-meant edit and quietly breaking the skill for everyone else.

The best moment to improve a skill is immediately after it disappoints you, in the same session. The failing case is already on screen, and if you corrected the output by hand, that correction is exactly the example the skill needs.

If Claude cannot run git where you are, which is the normal case in Cowork, step 5 changes shape: Claude gives you the finished text and a link straight to the file on GitHub. You paste, then press the green **Commit changes** button. No terminal, no clone, no branch.

## Get the skills

**If the library is distributed through organization settings, you do nothing.** The skills appear in Claude Code, Cowork, and claude.ai on their own, and pick up changes on their own once the marketplace is set to sync automatically. That is the intended state; the section below sets it up once.

Until then, install once per person:

- **Claude Code**

  ```
  /plugin marketplace add <owner>/<repo>
  /plugin install snotor-commands@claude-plugin
  ```

- **Cowork** - Customize, then Plugins, then Add marketplace, then enter `<owner>/<repo>` and install `snotor-commands`. Press Update on the marketplace to pick up changes.

Commands from a plugin are namespaced, so they appear as `/snotor-commands:jira-ticket` and so on.

## One-time setup for organization-wide distribution

This is what removes the install step for everyone, including people who will never open a terminal. An owner of the Claude Team or Enterprise plan does it once.

1. **The repository must live on github.com under the organization account, and it must be private or internal.** Public repositories are rejected for organization marketplaces, and a self-hosted git server cannot be used at all: the sync that feeds Cowork and claude.ai runs on Anthropic's side and reaches github.com or GitHub Enterprise Server only.
2. Install the Claude GitHub App on that repository.
3. In organization settings, under Plugins, connect the repository as a marketplace, and set it to sync automatically rather than on a manual trigger. Automatic sync is what makes an edit reach people without an administrator pressing anything.
4. Set the installation preference to installed by default.

After that, every merge to `main` reaches the whole team without anyone doing anything, in Claude Code, in Cowork, and in chat on the web.

## What makes a good skill

The skills here are project agnostic in the body, with anything project specific in a labelled **Project settings** block at the bottom, so another team can adopt one by editing that block alone.

`/skill` already applies the rules below, so you do not have to hold them in your head. They are written down for the times you edit a file directly.

- **The description decides whether the skill ever gets used.** It is the only text Claude sees before choosing a skill. Say what it does, then say when to reach for it using the words people actually type. Keep the whole line under about 1,000 characters.
- **Write the body as instructions, not encouragement.** "Read the entity file before naming a column" beats "be accurate".
- **Show one worked example of good output.** This is the single biggest difference between a skill that works and one that sort of works.
- **Say what never to do**, and what to do instead.
- **No inline shell injection.** The syntax that runs a command while the skill loads is replaced with a placeholder in Cowork sessions, so a skill that leans on it works for developers and quietly breaks for everyone else.
- **No credentials or personal data**, even though the repository is private. Skill text gets pasted into tickets and chat.
- **Keep it short enough to read in one sitting.** Long reference material belongs in a separate file next to `SKILL.md`.
- Plain hyphens, never em-dashes or en-dashes.

## Checks

Both run in CI on every push, and `/skill` runs them before publishing.

```bash
node scripts/validate.mjs
node scripts/catalog.mjs
```

`validate.mjs` blocks a skill whose frontmatter is malformed, whose name does not match its folder, whose description is missing or too long to survive the skill listing, which uses inline shell injection, or which contains something that looks like a credential. `catalog.mjs` rewrites the table above from the skills themselves.

If a skill is ever going to be uploaded to claude.ai directly rather than distributed as a plugin, `node scripts/validate.mjs --portable` reports the frontmatter fields that upload path rejects. Organization distribution makes that unnecessary, because plugin skills keep every field.

## Repository layout

```
.claude-plugin/marketplace.json     the marketplace manifest
plugins/snotor-commands/
  .claude-plugin/plugin.json        the plugin manifest
  skills/<name>/SKILL.md            one folder per skill
  skills/<name>/*.md                supporting files for that skill
scripts/validate.mjs                the checks
scripts/catalog.mjs                 regenerates the catalog table
scripts/package.sh                  zips for manual upload, only needed
                                    without organization distribution
```
